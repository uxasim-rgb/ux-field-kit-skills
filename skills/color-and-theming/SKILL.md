# Color and theming

This skill builds the color system and verifies it. It sits in the Craft band.

The governing idea: most color arguments are decidable. Contrast resolves to a number, gamut resolves to in or out, and an even ramp is produced by arithmetic rather than by judgement. Where a question has a calculable answer, calculate it and the argument ends.

**Works with:** `accessibility` owns the contrast thresholds this skill computes against · `design-systems` owns token naming conventions and versioning · `components-and-states` owns which states need which semantic color · `dataviz` owns categorical and sequential palettes for charts · `global-and-inclusive` owns cultural color meaning.

## Work in a perceptual color space

Pick OKLCH for new work. Its lightness axis corresponds to perceived lightness, which means a ramp generated by stepping lightness produces steps that look evenly spaced — something HSL does not give you.

The concrete failure with HSL: `hsl(60 100% 50%)` (yellow) and `hsl(240 100% 50%)` (blue) claim the same lightness and are wildly different to look at. Any ramp built by holding HSL lightness constant will have some steps that read as much darker than others.

`oklch(L C H)` — lightness 0–1 or 0–100%, chroma 0 to roughly 0.4, hue 0–360.

For an existing project, keep the existing notation. Consistency across the codebase is worth more than the better space, and a half-migrated palette is worse than either. Where you do migrate, do it in one pass with the values converted rather than re-picked.

Note that lightness in OKLCH is perceptual, not contrast. Two colors at L=0.5 are not guaranteed to have equal contrast against white — that still has to be computed.

## Generate ramps, do not pick them

A ramp is a series of steps of one hue used for backgrounds, borders, text and states. Picking each step by eye produces uneven jumps and accidental collisions.

Generate by stepping lightness on a curve, then correct by eye. A workable 11-step structure:

| Step | Lightness | Typical use |
| --- | --- | --- |
| 50 | ~0.98 | Page background tint |
| 100 | ~0.95 | Subtle surface |
| 200 | ~0.90 | Hover on a subtle surface |
| 300 | ~0.82 | Borders, dividers |
| 400 | ~0.70 | Disabled text, placeholder |
| 500 | ~0.60 | Non-text UI, icons |
| 600 | ~0.50 | Primary action, links |
| 700 | ~0.42 | Hover on primary |
| 800 | ~0.35 | Active, pressed |
| 900 | ~0.25 | Headings on light |
| 950 | ~0.15 | Highest-contrast text |

Chroma should peak in the middle of the ramp and fall toward both ends. Holding chroma constant makes the light steps look muddy and the dark steps look neon.

**Check gamut.** A high-chroma OKLCH value can fall outside sRGB and will be clipped, unpredictably, on displays that cannot show it. Either keep chroma inside sRGB, or provide an sRGB fallback and use `@media (color-gamut: p3)` for the wider version. A ramp that looks right on one display and wrong on another is usually a gamut problem.

Build the ramps you need — usually one neutral plus one brand plus semantic hues for success, warning and danger — and stop. A palette of twelve hues is a palette nobody will use consistently.

## Name by role, never by value

A token named for its value has to be renamed when the value changes, which is the one thing tokens exist to prevent.

| Bad | Why | Good |
| --- | --- | --- |
| `--blue-500` as a UI token | Breaks when brand becomes green | `--color-action` |
| `--light-gray` | Meaningless in dark mode | `--color-border-subtle` |
| `--red` | Says nothing about use | `--color-danger` |
| `--color-primary-button-bg-hover-dark` | Over-specified; one use only | `--color-action-hover` |

Two layers, and the distinction matters:

- **Primitives** — the raw ramp. `--blue-600`, `--neutral-100`. Named by value, because that is what they are. Never used directly in a component.
- **Semantic tokens** — the role. `--color-action`, `--color-surface`, `--color-text-muted`, `--color-border`, `--color-danger`. These reference primitives and are the only thing components use.

Theming then works by repointing semantic tokens at different primitives. A component that references `--blue-600` directly cannot be themed and will be found later, one at a time.

Keep the semantic set small enough to memorize. Surface, surface-raised, border, border-subtle, text, text-muted, text-inverse, action, action-hover, plus the status set, covers most products.

## Compute contrast, never estimate it

Contrast is a calculation on relative luminance. Eyeballing it is unreliable, especially for mid-tones and for colored text where the eye is easily fooled by saturation.

The thresholds — `accessibility` owns these; this skill owns computing against them:

| What | WCAG 2.2 AA | AAA |
| --- | --- | --- |
| Body text under 18.66px, or under 14px bold | 4.5:1 | 7:1 |
| Large text — 18.66px+, or 14px+ bold | 3:1 | 4.5:1 |
| UI components, focus indicators, graphical objects | 3:1 | — |
| Disabled controls | Exempt, but see below |

Check the pair that actually renders. Text on a gradient, on an image, on a translucent surface or on a hover background is a different pair from text on the base surface, and each has to pass. The commonest miss is checking against the page background when the text sits on a card.

Disabled controls are technically exempt. Making them illegible is still a usability problem — a user who cannot read a disabled field cannot tell what they would be filling in. Aim for 3:1 anyway.

A ratio that was not computed does not go in the report. This is the one rule in this skill with no exceptions.

## Never carry meaning by color alone

A status conveyed only by color is invisible to a substantial share of users and disappears in grayscale, in bright sun and on a cheap projector.

Pair color with a second signal: an icon, a label, a shape, a pattern, position. A red dot and a green dot become a red dot with a cross and a green dot with a tick.

Check by viewing the screen in grayscale. Anything that becomes ambiguous is a finding, and `accessibility` will treat it as one.

Red-green is the pairing to avoid for the primary distinction. Where success and failure must be distinguished, the icon is doing the work and the color is reinforcement.

## Dark mode is a different palette, not an inversion

Inverting a light palette produces harsh, vibrating results. Dark mode needs its own decisions:

- **Never pure black on pure white, or the reverse.** `#000` with `#fff` text produces halation that makes text shimmer. Use a very dark neutral — around L 0.15–0.20 — and a near-white around L 0.93–0.95.
- **Elevation reverses.** On light surfaces, raised things cast shadows. On dark surfaces, raised things get lighter, because shadows are invisible against dark. Build a surface ramp rather than a shadow ramp.
- **Desaturate.** Colors that look correct on light backgrounds glow on dark. Reduce chroma for the dark theme rather than reusing the same values.
- **Re-check every contrast pair.** Passing in light does not imply passing in dark, and the mid-tones are where it fails.
- **Respect the system.** `prefers-color-scheme` as the default, with an explicit override the user can set. A product that ignores the system preference and a product with no way to override it are both wrong.

Implement by redefining semantic tokens under the theme, never by filtering or inverting.

## Evidence bar

Every contrast claim is a computed ratio, reported to one decimal place with the two colors named. "Looks fine" is not a finding and neither is "seems low".

Gamut is checkable. A color outside sRGB with no fallback is a finding, because it will render differently across displays in a way nobody will reproduce in review.

Hue, brand direction and general aesthetic are preference, and preference is not a finding. Report a color choice only where it costs something nameable: a contrast failure, meaning carried by color alone, a token that cannot be themed, a gamut problem, or a collision with an established semantic meaning in the product.

Where a project has an established palette, review against it. Proposing a different hue because you would have chosen differently is how a color review gets ignored.

## Before you ship

| Symptom | What it means | Fix |
| --- | --- | --- |
| Ramp steps look unevenly spaced | Built in HSL or picked by eye | Generate by stepping perceptual lightness |
| Light steps look muddy, dark steps look neon | Chroma held constant | Peak chroma mid-ramp, fall at both ends |
| A color looks different on another display | Outside sRGB with no fallback | Clamp, or provide an sRGB fallback |
| Components reference `--blue-600` | Cannot be themed | Route through semantic tokens |
| A token is named `--light-gray` | Meaningless in dark mode | Rename by role |
| Contrast was judged by eye | Unreliable, especially mid-tone | Compute it; report the ratio |
| Contrast checked against the page, not the card | Wrong pair | Check the pair that renders |
| Status shown only by color | Invisible to many users and in grayscale | Add an icon or label |
| Dark mode is an inversion | Harsh, halation, wrong elevation | Separate palette; surface ramp for elevation |
| `#000` background with `#fff` text | Text shimmers | Near-black and near-white |
| Dark mode colors glow | Chroma not reduced | Desaturate for dark |
| Dark mode contrast was not re-checked | Light passing does not imply dark passing | Re-compute every pair |
| Twelve brand hues | Nobody will apply them consistently | Neutral, brand, and the status set |

## Reporting

**Severity ladder:** `Critical` — contrast below threshold on body text or a focus indicator, meaning carried by color alone on a status that matters · `Serious` — contrast below threshold on large text or UI components, a token that cannot be themed, dark mode pair failing · `Moderate` — off-ramp value, gamut issue with a fallback, inconsistent semantic use · `Minor` — naming inconsistency with no functional cost.

**Verification:** every reported pair computed and stated to one decimal; pairs checked in both themes; the pair checked is the one that renders; grayscale check performed; gamut checked; every component traced to a semantic token rather than a primitive.

**Format:** findings by principle, severity order, each with the two colors, the computed ratio, the threshold it misses, where it occurs, and the fix as a token change rather than a one-off value.

**Done when:** every contrast number in the report was computed, both themes were checked, nothing depends on color alone, and no component reaches past the semantic layer to a primitive.
